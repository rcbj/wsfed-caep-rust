# wsfed-caep

Rust port of the server-side WS-Federation relying party. Crate `wsfed-caep`, edition 2021. License MIT (`LICENSE`). A pull request merged into `main` publishes the crate to crates.io after the test workflow succeeds on that commit. A direct push does not. The token is the `CARGO_REGISTRY_TOKEN` repository secret. A release happens when the library's files changed since the last release's tag: `publish.yml` takes one patch above the highest published version, publishes it, and creates the matching tag and GitHub Release. A change to tests, the demo, or the docs releases nothing. To choose a version or start a new minor, raise `VERSION`; the version is stamped in CI and is not committed, so the manifests can trail what is published. When this tree is published, `develop` and `main` are the same commit.

## Usage

`RelyingParty::from_file("wsfed.json", None)`, then `login` and `handle_reply`. JSON keys are the Node keys.

The party accepts SAML 2.0 assertions with bearer confirmation `urn:oasis:names:tc:SAML:2.0:cm:bearer`. It reads IdP metadata, writes RP metadata, verifies XML signatures (rsa-sha256 is `http://www.w3.org/2001/04/xmldsig-more#rsa-sha256`), decrypts encrypted elements, and caches assertion ids. Status success is `urn:oasis:names:tc:SAML:2.0:status:Success`. The default subject attribute is `http://schemas.xmlsoap.org/ws/2005/05/identity/claims/nameidentifier`. `wsfed-caep generate-keys` writes a self-signed RSA key pair. The subject key identifier is the SHA-1 of the PKCS#1 public key. Exclusive canonicalization comes from `ua-cryptography-xml-c14n`. This crate does not link libxml2 and does not wrap a WS-Federation framework.

## signals

Omitted or `true` means on. The resolved configuration leaves `signals_set` false in that case, which is the omitted key. `false` sets `signals_set` and `signals` false. It does not start the receiver and does not require transmitter metadata. The relying party never starts the receiver itself; `SignalsReceiver` is separate. `stop` waits until the background poll loop has finished. `verify(state)` asks the transmitter for a verification event on the started stream (its `verification_endpoint`, `{stream_id, state}`); the demo's events tab uses it. Sign-in does not change when signals are off, because WS-Federation does not send OAuth scopes. A non-boolean raises a config error: `signals must be true or false`. The shipped demo omits the key.

**Plain http (#12).** `httpclient::send` is the one place every fetch goes through (metadata URL, SSF configuration, JWKS, stream and poll). `refuse_plain_http_off_loopback` parses with the `url` crate ureq dials with and refuses plain `http://` to a host that is not loopback (`127.0.0.0/8`, `::1`, `localhost`) before connecting, without resolving a name, naming only the scheme and host[:port]; userinfo is never loopback, and `refuse_unsafe_characters` refuses whitespace and control characters first (the WHATWG parser would drop tabs and newlines). Redirects are not followed (`redirects(0)`), so the checked URL is the only one dialled. No opt-out. `src/test_plain_http.rs` covers it; `http://0.0.0.0:<port>` reaches a 127.0.0.1 listener on Linux, so an empty backlog proves no connection was opened.

## Tests

```bash
docker build --target test .
```

The `test` stage runs `cargo test --all-features`, then `cargo test --lib pep_section_is_refused` (the default build refusing a `pep` section), in `rust:1-bookworm`. GitHub Actions uses that command. Do not run Cargo on the host. The demo image does not run the suite.

Rust covers the stub IdP (a signed SAML assertion the library accepts), replay, metadata, the self-signed certificate, the SSF poll receiver, the setup script's signals behavior, and the demo handler. No live iya-sts.

### Live sign-in and nightly

`python3 scripts/live_iya_sts.py` is the live half, on the host's Python. It starts a fresh iya-sts (main, memory mode, persistence and clustering off, no workers) unless `IYA_STS_URL` is set, or from `IYA_STS_IMAGE` when that is set. Its order is install script, then demo image build, then run: it copies the checkout (no `demo/generated`, `.git`, `target`) to a scratch context, builds the demo image there, runs `wsfed-caep generate-keys` inside it, registers the demo with `python3 scripts/configure_iya_sts.py` (standard library only, no `wsfed_caep` Python import, no Cargo; it writes the chain), builds again (only the `demo/` layer changes), checks the image's `demo/generated/idp-ca.pem` equals the saved file (`idpCaInImage` in the result), runs the demo with `rp.key`, `rp.crt` and `idp-metadata.xml` mounted file by file (never a CA, never a rewritten `idpCa`), signs in through `/authn-api`, emits credential-change and then session-revoked through `/admin-api/caep/emit`, and requires `GET /live-status` to show both, with `signedIn` false after the second. Ports default to `LIVE_STS_PORT=18517` and `LIVE_DEMO_PORT=18617`; never 3000, 8081, or 18481 to 18495. Containers: `iya-sts-live-wsfed-caep-rust`, `wsfed-caep-rust-live-demo`. The live script always starts a fresh iya-sts; the install script may be run again against the same one (an existing application gets the reply URL added, an existing user its password, the SSF grants are tolerated as already so; checked live with a real second run). No script prints a password or secret, or a URL (trace lines carry fixed labels). Secrets reach `docker run` as `-e NAME`, the value in the child's environment. A generated test-user password goes to `demo/generated/<user>.password` (created 0600) and only that path is printed. Every `ssl` context in `scripts/` sets TLS 1.2 as the minimum.

`GET /live-status` is JSON: `signedIn`, `subject`, `receiver`, and `events` (`type` as the full CAEP URI, and `jti`). No tokens or assertions. iya-sts main sets the assertion SessionIndex to the assertion id, so a session-revoked event finds nobody in the index. `App::remember` in `src/demo.rs` then ends the demo's one session and untracks it. That is demo code; the library is unchanged.

**The demo's PEP in one command.** `configure_iya_sts.py --pep [central|local]` (a bare `--pep` is `local`; `--pep-name`, default `pep-wsfed-demo`) does docs/remote-pep.md's steps 2–6 after the registration (`setup_pep`): the service account in `remote-peps` (created only if `/users?user=` says unknown), a P-256 key from the host's `openssl` in `generated/pep-key.pem` beside the config (0600, never printed, out of the image by `.dockerignore`), `issue-pep-credential` with its CSR and `application` = the realm when the key or account is new, else `set-pep-application`; the row `subject.acr` → `urn:example:acr`; the application's OWN policy (`fga-create-policy` allowing "already", name from `GET /applications?application=` → `page.fga.policy.name`, `import-alfa`, `fga-enable`), written while `page.fga.enforced` is not true, and rewritten on every run while its PolicyId is the script's own (`OWN_POLICY_IDS`, `urn:example:wsfeddemo-orders`; the live flip's `wsfeddemolocked` is not), with a `readAttributeProtected` rule (`attr1 == "abc123"`, `urn:sts:xacml:attribute:attr1`, subject category); never the realm root; `pep-policies-changed` added to `ssfAllowedEvents` only if the application restricts its events; then the `pep` section (`name`, `mode`, `assertionKey: file:generated/pep-key.pem`, relative to the config's directory as this library resolves it) with other members kept. `--dry-run` lists the PEP calls. ## Embedded PEP (#40)

iya-sts#1206 work item 8, behind the `pep` feature (`local` adds the engine). `src/pep.rs` wires in the shared `iya-pep` crate (rcbj/iya-pep-rust), the same way oidc-caep-risc-rust#47 does.
- `resolve_config` keeps the `pep` section in `Resolved::pep`, with `assertionKey` resolved against the configuration's directory. Without the feature, a `pep` section is refused rather than ignored.
- `RelyingParty::create`/`from_file` build and start the PEP once the metadata is read:
  - `pdpUrl` defaults to the IdP's entityID, which is iya-sts's realm issuer with the `/realm/<id>` prefix;
  - `application` defaults to `realm`;
  - `signals` is the library's, and `tlsCa` is `idpCa`;
  - an assertion key that is `privateKey` is refused, compared by JWK thumbprint.
- `SignalsReceiver::new` refuses a TLS client key equal to the PEP's. With `ReceiverOptions::pep` set, it adds `pep-policies-changed` to `events_requested` and registers the hand-over when the PEP wants events (`local`, or `central` with a Permit cache).
- `decide` and `decide_session` turn a `Login` into the PEP's subject through `pep::subject_of`:
  - The id is the `name` claim, else the NameID. iya-sts puts the username in both; `nameidentifier` is the opaque sub.
  - The properties are the attributes keyed by FriendlyName, else the Name's last segment, because catalogue properties are `[A-Za-z0-9_$@:-]` segments. Then `acr`, `amr` and `auth_time`.
  - `decide_session` denies a session the receiver no longer tracks (`SignalsReceiver::is_tracked`) or one past `SessionNotOnOrAfter`.
- The demo protects `/orders/<id>`. The image builds with `local`.
- `src/test_pep.rs` has its own stub PDP (tiny_http) and reuses `test_ssf.rs`'s transmitter stub.
- **The dependency is a git dependency on iya-pep-rust's `feature/1`** until that crate's first release. Switch it to the crates.io version then, because crates.io refuses a git dependency at publish.
- **The lock pins iya-pep `d88edef`** (feature/1): central hands `context.advice`; local writes the caller fact as the DN the registration names; `mode` defaults to `local` (a bare `--pep` in the install script too; a build without `local` that leaves `mode` out is refused at configuration); the poll period follows the stream state. The receiver reports that state to the PEP (`requested`/`excluded` at `start` and after a good poll, `down` after a failed poll and on `stop()`), held by `the_peps_stream_state_follows_the_polls` with `test_ssf.rs`'s stub failing its polls (`fail_polls`). `src/test_pep.rs`'s `pep_section` names `central`, which its tests were written for, and `a_section_without_a_mode_is_local` holds the default.
- **AuthZEN table (central == local).** `src/test_authzen.json` is this library's own table (catalogue rows, ALFA policies, directory people, 52 cases in phases `root` and `application`); `src/test_authzen_policies.json` is its XACML, generated by `python3 scripts/live_authzen.py --compile` with iya-sts's own compiler (IYA_STS_IMAGE) — regenerate it after changing the ALFA, never edit it. `src/test_authzen.rs` runs every case offline through a `local` party against a stub PDP (catalogue with `fgaApplications` in the `application` phase, policies, a register answer whose `identity` is a DN, PIP from the table's directory; the AuthZEN endpoint must never be asked). `authzen_live` does nothing unless `WSFED_AUTHZEN_LIVE` is set: `IYA_STS_IMAGE=iya-sts:live-2028-fga python3 scripts/live_authzen.py` starts `iya-sts-live-wsfed-caep-rust-authzen` on `LIVE_STS_PORT` (18517), registers the application (realm `http://127.0.0.1:<LIVE_DEMO_PORT>/authzen/`, a name only), adds the people, rows and policies, two PEP service accounts (`central`, `local`) with keys made in a scratch dir, runs the Rust test in `rust:1-bookworm` (`-v iya-pep-cargo:/cargo`, target `target/authzen-live`) per phase, and prints JSON: cases, `equal`, `asExpected`, `mismatches`, `storedDocuments` (iya-sts stores the same XACML), and on a mismatch `stsLog`. ## Layout

`src/` library. `src/bin/wsfed-demo.rs` and `src/bin/wsfed-caep.rs`. `scripts/configure_iya_sts.py` registers the demo with iya-sts; the container `PORT` wins over the shell `PORT`, and an explicit public URL wins over both. `scripts/trust_chain.py` saves the trust chain. `scripts/live_iya_sts.py` is the live sign-in (`--pep` with the demo's PEP). `scripts/live_authzen.py` is the AuthZEN central == local run. `Dockerfile` and comment-free `docker-compose.yml` use `network_mode: host`, `ENV PORT=3000`, and a health check of `http://127.0.0.1:${PORT}/healthz`.

## Demo

`PORT` defaults to 3000. Loopback realm and reply URLs follow the running port. Other hosts stay as written. `PUBLIC_URL` or `--public-url` replaces the origin and keeps the path. `GET /healthz` returns `200` and `ok`. `GET /live-status` is described above. The page links to `/login`, which redirects with `wa=wsignin1.0`, `wtrealm`, `wreply`, and `wctx`. The reply URL handles the POST and sign-out cleanup. `POST /logout` signs out. Demo JSON uses `file:` placeholders. Do not commit `demo/generated`.

## Trust chain (`idpCa`)

`idpCa` (default `file:generated/idp-ca.pem`, relative to `demo/`) is iya-sts's TLS listener CA trust chain. `scripts/configure_iya_sts.py` writes it on every run through `scripts/trust_chain.py`'s `save_trust_chain()` (the copy saml2-sp-rust carries; its CLI here reads `--config`/`WSFED_CONFIG` and `--idp`/`IYA_STS_URL`): the whole chain from `GET /tls/server-certificate` (leaf, TLS Issuing CA, Intermediate, Root), falling back to the handshake's chain, and prints the path, the anchor's subject and SHA-256. It used to keep only the root from the handshake, and only when the file was missing. `src/httpclient.rs` already adds every PEM block to the rustls root store, so the library needed no change. The demo image carries the chain from build time: `.dockerignore` is `demo/generated/*` then `!demo/generated/idp-ca.pem`, and the demo stage's `COPY demo demo` (after `cargo build`, which gets only `Cargo.*`, `src` and `demo/public` for `include_str!`, so a new chain does not rebuild the binaries) lands it at `/app/demo/generated/idp-ca.pem`. With no chain file the same COPY carries nothing from `demo/generated` and the build succeeds. Rebuild the image after re-running the install script against a different iya-sts. `src/test_trust_chain.rs` serves HTTPS from an openssl-made four-certificate chain and checks the registrar writes all four (published and handshake), that `RelyingParty` fetches metadata trusting the file, and that the leaf alone is refused.
